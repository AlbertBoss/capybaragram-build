# Сборка из исходников

[← К проекту](../README.md)

Проверенный путь — ручные workflow на стандартных GitHub Actions runner. Локальная сборка на произвольной машине отдельно не принята. Побайтовая воспроизводимость бинарных файлов не заявляется.

## Среда

| | Android | Windows |
| --- | --- | --- |
| Workflow | [android-candidate.yml](../.github/workflows/android-candidate.yml) | [windows-candidate.yml](../.github/workflows/windows-candidate.yml) |
| Runner | Ubuntu 24.04 | Windows 2025 |
| Инструменты | Temurin 17, SDK 36, Build Tools 36.0.0, NDK 27.2.12479018, CMake 3.22.1 | MSVC 14.44, Windows SDK 10.0.26100.0, Ninja Multi-Config |
| Результат | ARM64, `org.capybaragram`, API 23+ | x64, Release |

Версии upstream и подмодулей закреплены. Подготовка скачивает зависимости; SHA исходного репозитория не закрепляет автоматически каждый внешний ресурс.

## Параметры приложения

Нужны собственные Telegram `api_id` и `api_hash`, а также постоянный ключ Android-подписи. Имена Actions Secrets:

- `CAPY_API_ID`
- `CAPY_API_HASH`
- `CAPY_ANDROID_KEYSTORE_BASE64` — PKCS12 в Base64.
- `CAPY_ANDROID_KEYSTORE_PASSWORD`

Workflow ожидает alias `capybaragram-preview` и закреплённый публичный отпечаток сертификата. Для независимого форка создайте свой ключ и обновите ожидаемый отпечаток в своих workflow и проверках. Смена ключа уже установленного приложения нарушает обычную совместимость Android-обновления.

Не помещайте значения параметров, закрытые ключи, пароли и сессии Telegram в Git или артефакты CI. Параметры приложения не являются авторизацией пользователя. GitHub Secrets не делает скомпилированные API-параметры неизвлекаемыми из бинарного файла.

## Запуск

В Actions выберите workflow и Run workflow. Через авторизованный GitHub CLI, подставив свой репозиторий:

```sh
gh workflow run android-candidate.yml --repo OWNER/REPO --ref main
gh workflow run windows-release-toolchain.yml --repo OWNER/REPO --ref main
```

После успешной проверки Windows toolchain:

```sh
gh workflow run windows-candidate.yml --repo OWNER/REPO --ref main
```

Workflow запускаются вручную, без расписаний. Сборки одной платформы сериализуются без отмены работающего задания. Используются стандартные runner без настройки платных увеличенных машин.

## После сборки

1. Проверьте итоговый статус и скачайте артефакт до окончания срока хранения, указанного в workflow.
2. Сверьте SHA-256, сведения о сборке, Android-подпись и архитектуру.
3. Для нового артефакта обновите точные run ID и SHA в `android-client-smoke.yml` / `windows-client-smoke.yml` и соответствующих скриптах. Проверки намеренно привязаны к конкретным файлам.
4. Для установщика обновите run ID в `windows-installer.yml` и параметры в `ci/windows-installer/prepare_installer.py`.
5. Пройдите установку, нативные сценарии и отдельную приёмку на принадлежащих вам тестовых аккаунтах.

Стартовые тесты используют пустые профили, без запросов кода и входа пользователя.

## Профили Windows

Обычный профиль: `%APPDATA%/CapybaraGram Preview`. Переносной экземпляр использует `CapybaraGramForcePortable` рядом с EXE. Новый пустой каталог — отдельный профиль, требующий входа.

Обновление должно сохранять существующий профиль. Установщик проверен на сохранность синтетических файлов; сохранение действующей авторизации и совместимость формата проверяются отдельно. Встроенное автоматическое обновление отключено.

Ранние baseline и preview workflow оставлены как история этапов. Они имеют другие параметры и не являются актуальными кандидатами для установки. Для текущего пути используйте candidate workflow выше.
