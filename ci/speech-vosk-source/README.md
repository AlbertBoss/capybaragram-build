# Проверка сборки Vosk из исходников

Это отдельный эксперимент на Linux с публичными записями. Он не добавляет Vosk в
CapybaraGram и не заменяет уже измеренную библиотеку из wheel. Ранее старый бинарник
распознал пять записей при одном общем экземпляре модели, но завис при повторной
загрузке модели в том же процессе. Причина внутри библиотеки пока не установлена.

## Что закреплено

В `sources.json` указаны точные коммиты, размеры, SHA-256 архивов и проверенные файлы
сборки пяти компонентов: Vosk API, специального Kaldi, OpenFST, OpenBLAS и CLAPACK.
Локально сверены 24 569 файлов с Git; для 13 файлов Windows в архиве Kaldi отдельно
зафиксировано преобразование CRLF в LF, которое восстанавливает точный Git blob.
Эти файлы не участвуют в Linux-сборке. Ссылки из архивов не создаются; примеры,
обучение и внешние загрузчики Kaldi/API не извлекаются для сборки.

Выбор исторических коммитов Kaldi/OpenFST сделан нами для воспроизводимого теста.
Он не доказывает, что автор использовал эти коммиты при выпуске старого wheel.
OpenBLAS отдельно обновлён до закреплённой стабильной версии 0.3.34 и собирается
без Fortran/LAPACK, с `USE_THREAD=0`, `USE_LOCKING=1`, `NUM_THREADS=1`.
CLAPACK по-прежнему содержит старый LAPACK: это тестовый компонент, его допуск в
продукт требует отдельного рассмотрения. Полный аудит всех зависимостей не проведён.

## Порядок проверки

Ручной workflow `vosk-source-admission.yml` использует одноразовый Ubuntu-host без
ключей Telegram, профилей или собственных записей владельца. Архивы проверяются
до запуска кода. Перед компиляцией включается наследуемый запрет сетевых и Unix
сокетов через libseccomp; вызовы компиляторов разрешены. Это не полная изоляция
файловой системы. Официальные Ubuntu-пакеты инструментов устанавливаются до этого
запрета, их фактические версии записываются, но версии пакетов не закреплены.

Затем собственный C API распознаёт те же пять файлов PolyAI/minds14, что и предыдущий
эксперимент. Эталонные тексты не передаются в распознаватель. Второй ограниченный
процесс проверяет два цикла загрузки, распознавания и полного освобождения модели
с одной публичной девятисекундной записью. Оба процесса запрещают сетевые запросы
и запуск внешних программ до загрузки библиотеки. Результаты, код завершения,
тайм-ауты и пиковое потребление памяти сохраняются даже при ошибке.

Сборка ограничена 80 минутами исполнения команд, отдельными лимитами этапов и
95 минутами задания. Повторный запуск после ошибки не выполняется автоматически.
В артефакт попадают только отчёты и журналы; бинарники, модели и исходные архивы
этот workflow не публикует.

Успех на Linux ещё не подтверждает Android ARM64, Windows DLL, отмену из интерфейса,
переключение аккаунтов, безопасность всех компонентов или общую точность русского
распознавания. Исходный default Whisper Tiny клиента сохраняется.

Основа рецепта: [инструкции автора Vosk](https://alphacephei.com/vosk/install) и
[рецепты API v0.3.45](https://github.com/alphacep/vosk-api/tree/cf2560c9f8a49d3d366b433fdabd78c518231bec/travis).
Версия OpenBLAS выбрана с учётом [политики поддержки автора](https://github.com/OpenMathLib/OpenBLAS/blob/e0166008be8e466242aa76b2ff75ce3f0fbf574a/SECURITY.md).

## Исправление после первой сборки

[Первый запуск](https://github.com/AlbertBoss/capybaragram-build/actions/runs/37237447876)
собрал OpenBLAS, CLAPACK и OpenFST, но остановился при компиляции Kaldi:
его режим `HAVE_OPENBLAS` потребовал отсутствующий `lapacke.h`. В OpenBLAS
намеренно выключен LAPACK; реальные LAPACK-функции предоставляет CLAPACK/f2c.
Замена Android-ветки Kaldi на историческую Linux-ветку сама по себе этого не исправляет.

Новый рецепт копирует настоящие закреплённые `f2c.h` и `clapack.h`, исправляет
один макрос в сгенерированном `kaldi.mk` на `HAVE_CLAPACK` и передаёт тот же
режим Vosk API. Перед долгой компиляцией проверяются размер целого типа,
реальное умножение матриц CBLAS и решение системы уравнений CLAPACK.
Поддельный `lapacke.h` не создаётся. Исходный неудачный запуск сохранён;
исправление рецепта ещё не означает успешную сборку или допуск движка в клиент.
